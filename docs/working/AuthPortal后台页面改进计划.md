# AuthPortal 后台页面改进计划

> 状态：Working
> 更新时间：2026-08-02
> 适用范围：`Lumine.AuthPortal` 后台页面、AuthServer 管理接口及 OAuth2.1 / OIDC 联调流程
> 计划依据：登录后对左侧导航 12 个页面进行逐页打开、截图和功能完成度检查
> 当前进度：阶段 0、阶段 1已完成，阶段 2待实施

## 1. 计划目标

本计划用于把当前后台从“页面基本可打开”推进到“核心业务链路可验证、管理功能闭环、异常状态可解释、页面可长期维护”的状态。

完成后应满足：

- 登录后仪表盘能展示真实统计和 OIDC 服务状态。
- OAuth 客户端、授权确认、OIDC Discovery、Token 管理可以完成一条可复现的授权码流程。
- 用户、角色、权限、用户组和菜单之间的关系可以被完整维护。
- 系统配置、审计日志和 Token 管理具有明确的职责边界。
- 所有页面都有加载中、空数据、错误和成功反馈。
- 表格在常用窗口尺寸下不发生关键列截断；图标按钮具备可发现的提示。
- 关键改动有 API、前端交互、权限和浏览器回归验证。

## 3. 优先级定义

### P0：阻塞核心流程

影响登录后核心信息可信度或 OAuth2.1 / OIDC 主链路。P0 未完成前，不建议把后台作为联调基线。

### P1：补齐管理闭环

影响管理员能否真正维护系统，但不一定阻塞基础登录。P1 完成后，页面名称、菜单入口和实际能力应基本一致。

### P2：提升可用性和运营能力

包括列表效率、审计分析、视觉一致性、批量操作、导出和长期维护质量。

## 4. 分阶段实施计划

### 阶段 0：建立统一运行基线（P0，已完成）

### 目标

先消除环境地址和数据读取方式不一致的问题，确保后续页面验证使用同一套 API、Issuer 和客户端配置。

### 任务

- 梳理前端 API 基地址、服务端 Issuer、OIDC 客户端配置、Redirect URI 和 Browser 调试地址的来源。
- 清理页面中出现的固定本地端口，禁止 Consent、OIDC Discovery、Dashboard 各自维护不同的默认地址。
- 将本地开发地址、容器地址和部署地址区分为配置项，避免把开发地址写入生产默认配置。
- 在 OIDC 联调页增加“当前服务地址、Issuer、客户端 ID、回调地址”的只读诊断摘要。
- 对回调地址做格式、协议、端口和客户端白名单校验；校验失败时禁止进入下一步，并显示可操作的错误信息。
- 确认 `PortalApiClient`、Session、OIDC 页面 ViewModel 与 AuthServer 端点使用同一套路径约定。

### 涉及位置

- `Lumine.AuthPortal/Lumine.AuthPortal/ViewModels/MainViewModel.cs`
- `Lumine.AuthPortal/Lumine.AuthPortal/ViewModels/Pages/AuthPageViewModels.cs`
- `Lumine.AuthPortal/Lumine.AuthPortal/ViewModels/Pages/DashboardPageViewModel.cs`
- `Lumine.AuthPortal/Lumine.AuthPortal/Services/PortalApiClient.cs`
- `Lumine.AuthServer/Program.cs`
- `Lumine.AuthServer/appsettings.json`
- `Lumine.AuthServer/appsettings.Development.json`
- OIDC Controller、OIDC Service 及对应文档

### 验收标准

- 页面中不再出现未经配置的旧本地端口。
- 同一个客户端的 Redirect URI 在客户端管理、授权确认和 OIDC Discovery 页面中显示一致。
- 使用同一套配置可以完成 Authorize、Consent、Token、UserInfo 四步流程。
- 修改本地端口后只需要修改配置，不需要修改页面代码。

### 阶段 1：修复仪表盘真实数据（P0，已完成）

### 目标

将仪表盘从静态布局和占位卡片提升为登录后的真实系统摘要。

### 任务

- 检查仪表盘摘要 API 是否实际被调用，核对请求路径、授权 Token 和响应 DTO。
- 将四张统计卡片拆分为明确的加载中、加载成功、无数据和请求失败状态。
- 展示用户数、角色数、权限数、OAuth 客户端数，并标注统计时间。
- 展示近 7 天登录趋势和 Token 签发趋势；无数据时显示“暂无业务数据”，不使用与加载中相同的 `--` 状态。
- 展示最近登录用户和 OIDC Discovery 摘要；失败时提供重试按钮和具体原因。
- 刷新仪表盘时保留上一次数据，避免整个页面闪烁为空。

### 验收标准

- Admin 登录后不再出现四张统计卡片全部为 `--`。
- API 失败、数据库为空和加载中三种状态可被视觉区分。
- 点击刷新后能重新请求并更新统计时间。
- 未授权用户不能通过前端隐藏按钮绕过服务端权限检查。

### 阶段 2：打通 OIDC 授权闭环（P0）

#### 2.1 OIDC Discovery 页面

- 将页面按钮明确标注为“获取授权码”“换取 Token”“读取 UserInfo”，并显示当前步骤状态。
- `重置 PKCE` 后清空旧的 authorize、token 和 user info 结果，重新生成 state、nonce、code challenge。
- 每一步显示请求时间、成功/失败状态和可读错误信息。
- 授权码、Access Token、ID Token 等敏感结果默认脱敏或折叠，提供明确的复制按钮和清空按钮。
- 在开发环境显示调试参数；生产环境隐藏 state、nonce、code challenge 等内部参数。
- 对 UserInfo 响应使用结构化 JSON 展示，避免长文本挤压布局。

#### 2.2 授权确认页面

- 授权确认页必须读取真实的 authorize 请求，而不是使用固定 Demo 数据。
- 用人类可读的名称解释 Scope，例如“读取用户信息”“读取角色”“读取权限”。
- 展示客户端名称、客户端 ID、回调地址、请求时间和授权有效期。
- 批准和拒绝都要有明确的处理中、成功和失败状态。
- 批准后显示下一步位置；拒绝后返回标准 OAuth 错误响应，不直接吞掉异常。
- 对 state、nonce、code challenge 和授权码有效期进行服务端校验。

#### 2.3 Token 管理页面

- 展示 Token 类型、用户、客户端、Scope、签发时间、过期时间、状态和撤销时间。
- 增加按用户、客户端、状态和过期范围筛选。
- 提供单条撤销和批量撤销，并要求二次确认。
- 对没有 Token 的情况说明“完成授权码换 Token 后才会出现记录”，同时提供跳转 OIDC 联调页的入口。
- 不在页面日志、错误提示或截图中输出完整 Token。

### 验收标准

- 使用当前 Demo Client 可重复完成：Authorize → Consent → Authorization Code → Token → UserInfo。
- Consent 页面批准后能回到正确 Redirect URI。
- Token 管理页能看到新生成的 Refresh Token/Token 记录，并能撤销后刷新状态。
- 失败场景至少覆盖无效 client、无效 redirect URI、Scope 不允许、code 重复使用、PKCE 不匹配和过期 code。

### 阶段 3：补齐身份与菜单管理闭环（P1）

#### 3.1 用户组管理

- 明确用户组与角色、权限、成员之间的模型关系。
- 增加用户组新增、编辑、删除和启停能力。
- 增加成员加入、移除和批量分配能力。
- 支持从用户组详情页查看并修改角色/权限映射。
- 删除用户组前检查成员和角色依赖，提供保护性提示。
- 若当前后端没有用户组写入接口，应先补齐 DTO、应用服务、Controller、权限标注和测试，再接入页面。

#### 3.2 菜单管理

- 将菜单项定义统一为名称、分组、排序、路由、图标、所需权限、可见性和实现状态。
- 增加拖拽排序或上移/下移操作。
- 增加菜单编辑、启用/停用和权限绑定。
- 校验路由唯一性、父子关系和权限编码有效性。
- 将左侧实际导航与菜单配置使用同一数据源，避免“菜单管理页面显示一套，左侧导航写死另一套”。
- 对未实现页面提供明确标识，不允许菜单标记为已实现但点击后进入占位页。

#### 3.3 权限管理与角色管理

- 权限按模块分组显示，支持模块筛选和权限编码搜索。
- 角色权限支持全选、反选、按模块批量分配。
- 删除角色前展示关联用户数量和影响范围。
- 记录角色权限变更的操作者、时间和变更前后差异。
- 对系统内置 Admin 角色增加删除和降权保护。

### 验收标准

- 管理员可以不依赖数据库脚本完成用户组、角色、权限和菜单的常规维护。
- 新增权限绑定到角色后，左侧菜单和页面按钮可按权限立即更新。
- 无权限用户无法通过直接访问路由或调用 API 获得受保护数据。
- 所有新增写入操作均有成功、失败、重复和权限不足提示。

### 阶段 4：系统配置与审计能力（P1/P2）

#### 4.1 系统配置

先明确系统配置的边界：

- 客户端体验设置：主题、分页大小、布局偏好，可由管理员保存。
- 服务端运行配置：Issuer、Token 有效期、客户端默认值等，只显示安全摘要，不在页面泄露 Secret。
- 环境变量和部署级配置：继续由部署配置管理，不允许后台页面直接修改敏感环境变量。

具体任务：

- 为主题和分页设置提供保存、恢复默认和重置成功提示。
- 显示配置来源和最后读取时间。
- 对只读配置明确标记“由部署环境管理”。
- 对敏感值只显示掩码、是否配置和更新时间。
- 配置变更后刷新当前页面并验证新设置已生效。

#### 4.2 审计日志

- 增加时间范围、分类、动作、操作者、目标和结果筛选。
- 支持分页、排序、关键字搜索和清空筛选条件。
- 增加详情面板，展示请求关联 ID、来源、目标、结果和失败原因。
- 增加 CSV/JSON 导出，并限制导出权限和数据范围。
- 对登录、登出、授权确认、授权码签发、Token 换取、Token 撤销、用户/角色/权限变更建立统一事件编码。
- 保持审计记录只追加，不允许普通管理员修改或删除。

### 验收标准

- 系统配置改动不会泄露密码、Client Secret 或完整 Token。
- 审计日志可以定位一次授权失败的操作者、客户端、时间、目标和原因。
- 大量日志下分页查询不会一次性加载全部数据。

### 阶段 5：统一页面体验和可维护性（P2）

### 表格与布局

- 统一所有管理列表的表头、行高、空状态、分页和状态消息样式。
- 处理 1280×720 常用窗口下的列截断，长 ID、Redirect URI、Scope 使用 Tooltip、复制按钮或详情面板。
- 对表格提供横向滚动或自适应列，而不是把最后一列裁掉。
- 统一页面内容最大宽度、卡片间距、标题和说明文字层级。
- 对 OIDC、系统配置等较长页面提供明确的滚动区域和固定操作区。

### 交互与可访问性

- 所有图标按钮必须有 Tooltip、键盘焦点状态和可读的辅助名称。
- 删除、撤销、停用等危险操作统一使用二次确认。
- 保存按钮在请求期间禁用，避免重复提交。
- 网络失败时保留用户输入，并提供重试。
- 空状态提供下一步动作，例如“新增客户端”“前往 OIDC 联调”“刷新数据”。
- 支持深色主题下的对比度检查和状态色辨识。

### 错误与诊断

- 统一错误模型：用户提示、技术详情、请求关联 ID 分开处理。
- 前端不直接展示异常堆栈和数据库连接信息。
- 为关键页面增加开发环境诊断信息，生产环境仅保留安全摘要。
- 对 API 401、403、404、409、429 和 500 提供不同文案及处理方式。

## 5. 建议的实现顺序

1. 统一 API、Issuer、客户端和 Redirect URI 配置。
2. 修复仪表盘统计和加载/错误状态。
3. 打通 OIDC Discovery、授权确认和 Token 管理闭环。
4. 补齐用户组管理写入能力。
5. 将菜单管理从只读检查升级为可维护配置。
6. 明确并实现系统配置边界。
7. 增强 Token 生命周期和审计筛选能力。
8. 优化用户、角色、权限、客户端列表的批量操作和响应式布局。
9. 完成全量浏览器回归和部署验证。

## 6. 验证计划

### 后端与解决方案

在仓库根目录执行：

```powershell
dotnet build .\Lumine_AuthService.sln
```

涉及数据库模型、权限或 OIDC 逻辑时，补充：

```powershell
dotnet test .\Lumine_AuthService.sln
```

本地数据库初始化：

```powershell
.\scripts\init-local-db.ps1
```

### API 验证

至少验证：

- 登录、刷新会话和退出登录。
- 用户、角色、权限、客户端列表读取。
- 用户/角色/权限/客户端新增、编辑、删除和权限不足。
- OIDC Discovery 文档地址和 Issuer 一致。
- Authorize、Consent、Token、UserInfo 全流程。
- Token 撤销后不能继续使用。
- 审计日志能记录认证和管理操作。

### 浏览器回归矩阵

每个页面至少检查：

| 检查项 | 通过标准 |
| --- | --- |
| 首次打开 | 页面标题、导航选中项和主体内容正确 |
| 加载状态 | 不显示错误的空数据或旧数据 |
| 空数据 | 有明确说明和下一步操作 |
| 请求失败 | 有用户可理解的错误和重试入口 |
| 权限不足 | 页面和 API 都拒绝越权访问 |
| 写入操作 | 成功提示、列表刷新、失败保留输入 |
| 危险操作 | 有二次确认，取消后数据不变 |
| 窗口尺寸 | 1280×720 下关键字段和操作不被裁剪 |
| 深色主题 | 文本、边框、状态色仍可辨识 |

## 7. 风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| OIDC 配置统一时改变现有回调行为 | Demo Client 或外部客户端无法登录 | 先建立客户端配置快照，逐个验证 Redirect URI，再更新文档和种子数据 |
| 用户组与现有角色权限模型重复 | 数据关系复杂、权限判断不一致 | 先明确 User → Group → Role → Permission 关系，避免新增平行权限链 |
| 后台配置误修改部署敏感项 | Secret 泄露或服务不可用 | 敏感配置只读摘要，写入配置仅限明确允许的体验项 |
| 菜单配置与代码注册不一致 | 菜单可见但页面不可用 | 建立路由注册校验，启动或刷新菜单时报告失效路由 |
| 审计日志数据量增长 | 查询慢、导出耗时 | 服务端分页、索引、时间范围限制和异步导出 |
| 前端只修视觉不修 API 状态 | 页面看似完整但业务仍不可用 | 每个页面必须绑定 API 成功、失败、空数据和权限不足验收项 |

## 8. 完成定义

本计划可以标记为完成，需同时满足：

- P0 任务全部通过端到端验证。
- P1 页面名称与实际能力一致，不再把只读页面称为管理页面。
- 12 个导航页面均有明确的加载、空数据、错误和权限状态。
- 关键管理操作均有 API 权限校验、前端反馈和审计记录。
- OIDC 流程在本地开发、Docker 调试和部署配置下分别验证通过。
- `dotnet build`、相关测试和浏览器回归矩阵通过。
