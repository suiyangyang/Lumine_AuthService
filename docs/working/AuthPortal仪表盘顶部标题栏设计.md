# AuthPortal 仪表盘顶部标题栏设计

> 状态：Working
> 更新时间：2026-08-03
> 适用范围：`Lumine.AuthPortal` 仪表盘首页顶部标题栏
> 关联提交：`da7f729 fix: 修复仪表盘数据加载与导航滚动`

## 1. 设计结论

当前顶部区域同时承担页面标题、状态说明、更新时间、服务地址输入和刷新操作，导致标题栏高度偏大，且把开发诊断信息和日常管理信息混在了一起。

推荐将标题栏改为“单行主操作栏 + 可选诊断区”两层结构：

```text
系统概览                         ● 认证服务正常   最近更新 23:10   [刷新]
系统总体信息加载完成
```

服务地址不再占据首页顶部的固定空间。开发环境需要修改地址时，通过诊断区或系统配置入口打开；生产环境只展示只读的服务摘要。

## 2. 当前问题

当前实现位于：

- `Lumine.AuthPortal/Lumine.AuthPortal/Views/Pages/DashboardPageView.axaml`
- `Lumine.AuthPortal/Lumine.AuthPortal/ViewModels/Pages/DashboardPageViewModel.cs`

标题栏使用两行网格，右侧垂直排列服务地址输入框和“刷新仪表盘”按钮。它带来以下问题：

1. 标题、说明、更新时间和配置输入形成多行堆叠，首屏被顶部区域占用。
2. 服务地址是开发诊断信息，不是管理员每次进入首页都需要操作的业务信息。
3. “刷新”是高频操作，却被放在右侧第二行，视觉优先级不够清晰。
4. OIDC Discovery 摘要已经位于页面下方，顶部再放完整地址会造成信息重复。
5. 1280×720 窗口下，顶部高度增加后会压缩趋势图和最近登录区域的可视空间。

## 3. 目标与非目标

### 目标

- 将首页标题栏控制在约 64—76px 的有效高度。
- 首屏一眼看到页面名称、服务状态、最近更新时间和刷新入口。
- 保留必要的开发诊断能力，但不让服务地址占据主操作区。
- 保持现有加载、成功、失败和“保留上一次数据”的行为。
- 在浅色和深色主题下都能区分正常、警告和失败状态。

### 非目标

- 本次不引入新的健康检查服务。
- 本次不把数据库、Token 或 OIDC 拆成虚假的独立服务状态。
- 本次不修改认证、OIDC、权限或 Dashboard API 的业务语义。
- 本次不在标题栏加入用户管理、全局搜索等新的大型功能。

## 4. 推荐布局

### 4.1 主标题栏

使用水平布局，左侧自适应，右侧固定操作区：

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 系统概览                         ● 认证服务正常   最近更新 23:10  ↻ │
│ 系统总体信息加载完成                                                   │
└─────────────────────────────────────────────────────────────────────┘
```

推荐信息排列：

左侧：

- 页面标题：`系统概览`，字号从当前 24px 降为 20—22px。
- 次级状态：`系统总体信息加载完成`、`正在加载…` 或 `刷新失败，仍显示上次数据`。
- 次级状态最多一行，过长时截断并通过 Tooltip 查看完整内容。

右侧：

- 服务状态：`● 认证服务正常`。
- 更新时间：`最近更新 23:10`。
- 刷新按钮：优先使用带文本的 `刷新`，窄窗口时允许退化为带辅助名称的图标按钮。

右侧不建议加入完整 Issuer、数据库地址或当前用户角色；这些信息要么属于诊断信息，要么已由全局壳层承担。

### 4.2 诊断区

服务地址输入框移动到标题栏下方的可折叠诊断区，默认收起：

```text
[显示连接诊断]

服务地址  http://localhost:13255                         [应用并刷新]
Issuer    http://localhost:13255
```

规则：

- 开发环境显示“显示连接诊断”，允许修改服务地址。
- 生产环境只显示当前服务地址和 Issuer 的脱敏或只读摘要。
- 修改地址后仍复用现有 `RefreshAsync` 流程，不在 View 中直接发 HTTP 请求。
- 诊断区展开状态不影响标题栏固定高度。

如果当前阶段不想增加折叠交互，可以先将服务地址移动到系统配置页，标题栏只保留服务状态、更新时间和刷新按钮。

## 5. 状态设计

状态文案和颜色不能只依赖颜色表达：

| 状态 | 标题栏文案 | 视觉状态 | 操作 |
| --- | --- | --- | --- |
| 首次加载 | 正在加载系统概览 | 中性/加载 | 刷新按钮禁用 |
| 加载成功 | 认证服务正常 | 绿色圆点 + 文案 | 可刷新 |
| 部分可见 | 系统概览已加载 · 受权限限制 | 蓝色或中性色 | 可刷新 |
| 刷新失败但有旧数据 | 刷新失败 · 正在显示上次数据 | 黄色/警告 | 可重试 |
| 首次加载失败 | 无法加载系统概览 | 红色/错误 | 显示重试 |
| OIDC Discovery 失败 | OIDC 配置不可用 | 红色/错误 | 显示诊断入口 |

“认证服务正常”只能在 Discovery 和 Dashboard 摘要都成功后显示。不能仅因为页面已经打开就显示正常。

## 6. 数据与代码设计

第一版不需要新增 API。现有数据足以支持：

- `GetDiscoveryAsync` 成功：说明 OIDC Discovery 可访问。
- `GetDashboardSummaryAsync` 成功：说明仪表盘摘要可访问。
- `GeneratedAtUtc`：显示最近成功更新时间。
- `HasLoadError` 与 `HasLoadedData`：区分首次失败和刷新失败。

建议在 `DashboardPageViewModel` 增加派生属性，而不是改变 DTO：

- `ServiceStatusText`
- `ServiceStatusKind`
- `ShowConnectionDiagnostics`
- `ConnectionDiagnosticsExpanded`
- `RefreshButtonText`

标题栏只绑定 ViewModel，不直接读取 `_apiClient` 或执行网络请求。

后续如果需要展示数据库健康状态，应新增真实的 health check 或诊断接口，并明确权限和信息泄露边界；不应在本次标题栏改造中预留虚假的“数据库正常”。

## 7. 响应式规则

以 1280×720 为主要验收尺寸：

- 标题栏右侧至少保留服务状态、更新时间和刷新按钮。
- 服务状态文案可缩短为 `服务正常`，但不能只剩颜色或图标。
- 地址输入框不得出现在默认首屏布局中。
- 标题栏不允许因为右侧内容把正文横向撑开。
- 右侧空间不足时，先隐藏诊断入口，再压缩状态文案，最后将刷新按钮退化为图标按钮。
- 趋势图和最近登录区域应在首屏获得更多可视高度。

## 8. 四阶段实施设计

四个阶段按“先压缩空间，再稳定状态语义，最后增加诊断和运营信息”的顺序推进。前两个阶段不改变 Dashboard API，第三阶段主要增加前端交互，第四阶段才允许扩展后端数据契约。

| 阶段 | 目标 | API 变化 | 主要产物 |
| --- | --- | --- | --- |
| 第一阶段 | 压缩标题栏并移除首屏配置输入 | 无 | 更紧凑的主标题栏 |
| 第二阶段 | 统一状态、更新时间和刷新反馈 | 无 | 可解释的状态模型 |
| 第三阶段 | 补齐诊断区、响应式和可访问性 | 原则上无 | 可折叠诊断入口和窄窗口布局 |
| 第四阶段 | 接入真实安全运营信号 | 可能新增 DTO/接口 | 紧凑风险摘要和详情跳转 |

### 8.1 第一阶段：低风险结构压缩

#### 目标

在不改变数据请求和权限逻辑的前提下，减少标题栏的垂直占用，把服务地址输入框移出主操作区。

#### 界面改动

将当前“左侧标题 + 右侧垂直堆叠 TextBox/按钮”的结构改为：

```text
┌──────────────────────────────────────────────────────────────┐
│ 系统概览                         最近更新 23:10       [刷新] │
│ 系统总体信息加载完成                                             │
└──────────────────────────────────────────────────────────────┘
```

- 标题栏外层保留一个 `Border`，减少不必要的嵌套高度。
- 左侧使用 `StackPanel`，标题和状态说明保持两行。
- 右侧使用水平布局，暂时只放更新时间和刷新按钮。
- 当前 `BackendBaseUrl` 输入框移到诊断区占位位置，第一阶段可以先隐藏于主界面之外，保留 ViewModel 绑定和刷新逻辑。
- 标题字号从 24px 调整为 20—22px，主标题栏内边距控制在 14—16px。
- 刷新按钮不再使用“刷新仪表盘”长文案，统一为“刷新”；完整含义通过 Tooltip 和辅助名称提供。

#### 代码边界

- 只修改 `DashboardPageView.axaml` 的布局和文案。
- 不修改 `DashboardController`、`DashboardSummaryDto` 或 `PortalApiClient`。
- 保留 `DashboardPageViewModel.RefreshAsync` 的请求顺序、错误处理和旧数据保留逻辑。
- `LastUpdatedText` 继续使用服务器返回的 `GeneratedAtUtc`，不使用客户端点击时间冒充数据更新时间。

#### 阶段验收

- 1280×720 下标题栏高度明显下降，趋势图区域向上移动。
- 首屏默认不显示可编辑服务地址。
- 点击刷新仍然执行原有刷新命令，按钮在请求期间不可重复点击。
- 首次加载、加载成功、刷新失败和首次失败的现有状态没有回归。

### 8.2 第二阶段：信息重排与状态语义统一

#### 目标

让标题栏右侧显示真正有价值且可以被验证的信息，而不是只把控件挤到一行。状态、更新时间和刷新入口需要形成稳定的视觉和数据关系。

#### 推荐排列

```text
左侧：系统概览
      系统总体信息加载完成

右侧：● 认证服务正常   最近更新 23:10   [刷新]
```

右侧信息的优先级固定为：

1. 服务是否可用；
2. 当前数据是否新鲜；
3. 用户能否立即刷新。

用户姓名、当前角色、完整 Issuer、数据库地址和 Token 数量不放进这一阶段的标题栏。它们要么属于全局壳层，要么属于诊断或业务卡片。

#### ViewModel 设计

建议在 `DashboardPageViewModel` 增加派生属性：

- `ServiceStatusText`：例如 `认证服务正常`、`OIDC 配置不可用`。
- `ServiceStatusKind`：例如 `Loading`、`Healthy`、`Warning`、`Error`、`Restricted`。
- `ServiceStatusAccessibilityText`：为屏幕阅读器提供不依赖颜色的完整描述。
- `RefreshButtonText`：正常时为 `刷新`，请求中为 `刷新中…`。
- `ShowLastUpdated`：只有成功获取过摘要后才展示更新时间。

可以用枚举表达 `ServiceStatusKind`，避免在 View 中比较中文文案。颜色、图标和文本均由同一状态派生，但文本必须始终显示。

#### 状态判定

| Discovery | Dashboard 摘要 | 状态 |
| --- | --- | --- |
| 加载中 | 未开始/加载中 | Loading |
| 成功 | 成功 | Healthy 或 Restricted |
| 成功 | 失败 | Error |
| 失败 | 未请求/失败 | Error |
| 成功 | 成功后刷新失败 | Warning，保留旧数据 |

当四张统计卡片中存在权限不可见项时，状态可以是 `Restricted`，但不能把权限受限误报为服务故障。

#### 代码边界

- `GetDiscoveryAsync` 和 `GetDashboardSummaryAsync` 仍由现有 `RefreshAsync` 统一调用。
- 状态计算集中在 ViewModel 的一个私有方法中，不散落在 XAML 的多重条件绑定里。
- 不新增客户端请求，不改变服务端返回结构。
- 服务状态颜色应绑定主题资源，例如正常、警告、错误和中性状态资源，不能在 XAML 中硬编码多套颜色。

#### 阶段验收

- 标题栏能明确区分“服务正常”“权限受限”“首次失败”和“刷新失败但保留旧数据”。
- 更新时间只代表最近一次成功摘要的服务器时间。
- 刷新中有明确的忙碌状态，按钮不可重复提交。
- 深色主题下状态文本、图标和键盘焦点均可辨识。

### 8.3 第三阶段：诊断区、响应式与可访问性

#### 目标

保留开发环境快速切换服务地址的能力，同时避免配置输入重新占满标题栏；并让标题栏在 1280×720、窄窗口和高 DPI 场景下保持可用。

#### 诊断区交互

标题栏右侧增加低优先级入口：

```text
● 认证服务正常   最近更新 23:10   [诊断] [刷新]
```

点击“诊断”后在标题栏下方展开：

```text
┌──────────────────────────────────────────────────────────────┐
│ 服务地址  [http://localhost:13255                         ] │
│ Issuer    http://localhost:13255                              │
│ Discovery 可访问 · 摘要接口可访问             [应用并刷新] │
└──────────────────────────────────────────────────────────────┘
```

规则：

- 诊断区默认收起，且不参与主标题栏高度计算。
- 输入框继续绑定 `BackendBaseUrl`，应用操作仍调用现有 `RefreshCommand`。
- 输入地址前先执行现有 `AppEnvironment.TryNormalize`，失败时只显示地址校验错误，不发请求。
- 应用新地址时清除旧的错误提示，但不在请求尚未成功前伪造新的服务状态。
- 生产环境不显示可编辑输入框；可以展示只读地址摘要或直接隐藏诊断入口。
- 不在诊断区显示 Client Secret、完整 Token、Cookie、密码或连接字符串。

如果 Avalonia 当前项目不适合增加折叠控件，第三阶段可以将“诊断”改为跳转系统配置页；主标题栏仍然只保留状态、更新时间和刷新。

#### 响应式规则

由于 Avalonia 页面没有依赖浏览器 CSS 的断点机制，采用“内容优先级降级”而不是强制固定断点：

1. 宽窗口：显示完整服务状态、完整更新时间和文字按钮。
2. 中等宽度：缩短为 `服务正常`、`更新 23:10`，保留文字按钮。
3. 窄窗口：刷新按钮退化为图标按钮，必须有辅助名称和 Tooltip。
4. 极窄窗口：右侧信息允许换到第二行，但不允许把地址输入框放回默认标题栏。

布局应使用 `Grid` 的 `*` 与 `Auto` 列，避免固定宽度；状态文本设置最大宽度，必要时截断。不能通过增大整个页面的最小宽度来掩盖标题栏布局问题。

#### 可访问性规则

- 服务状态提供文本和辅助名称，不能只使用圆点颜色。
- 刷新按钮提供“刷新仪表盘数据”的辅助名称。
- 诊断按钮提供“展开连接诊断”或“收起连接诊断”的动态辅助名称。
- 所有按钮具备清晰的键盘焦点边界。
- 状态变化应通过可读文本体现；不依赖动画或颜色变化作为唯一提示。
- 高 DPI 下不使用过小的图标点击区域，按钮保持可操作尺寸。

#### 阶段验收

- 诊断区默认收起，且不会让主标题栏恢复为多行大块布局。
- 修改服务地址后仍能复用原有规范化、刷新和错误反馈流程。
- 1280×720 和窄窗口下无横向溢出、标题截断可解释、刷新入口仍可发现。
- 键盘可以到达诊断和刷新按钮，深色主题下焦点边界清晰。

### 8.4 第四阶段：真实运营信息与详情下钻

#### 目标

只有在后端具备可靠统计口径后，才在标题栏右侧加入少量高价值运营信号。标题栏只显示摘要，详细内容下沉到页面卡片、审计日志或 Token 管理页。

#### 推荐信息

右侧最多增加一个紧凑的“待处理”摘要，不同时堆叠多个数字：

```text
● 服务正常   待处理 3   最近更新 23:10   [刷新]
```

“待处理 3”点击后进入对应详情，或滚动到首页的“管理员待处理事项”区域。优先级建议为：

1. 近期认证失败达到风险阈值；
2. 即将过期的 Refresh Token；
3. 配置不完整或客户端异常；
4. 审计事件需要管理员处理。

不建议在标题栏同时显示“用户 6、客户端 1、Token 12”等统计数字，因为这些数字已经属于首页统计卡片，重复展示会增加噪声。

#### 后端数据设计

第四阶段才考虑扩展 `DashboardSummaryDto`，可新增独立的可选结构，例如：

```text
OperationalSignals
├── FailedLogins24h
├── ExpiringRefreshTokens7d
├── ClientConfigurationWarnings
└── PendingAuditEvents
```

设计约束：

- 每个数字必须有时间窗口、统计口径和权限边界。
- 登录失败必须来自统一审计事件，不能只依赖前端错误次数。
- Token 数量应明确是 Refresh Token，不能把无状态 Access Token 伪装成可查询库存。
- 客户端异常必须定义具体规则，例如缺少有效 Redirect URI，而不是凭空判断。
- 无权限时返回不可见或脱敏状态，不能通过数量差异泄露受保护数据。
- 大量审计数据统计要有时间范围和索引，不能每次打开首页扫描全表。

如果这些信号需要独立权限，优先使用明确的读取权限并同步更新权限清单、接口文档和前端菜单权限；不要让标题栏绕过现有权限模型。

#### 健康状态边界

“认证服务正常”可以由现有 Discovery 和 Dashboard 摘要请求成功推导。数据库、外部依赖或 Token 服务状态只有在存在真实 health check 或诊断接口时才可以加入。每个健康检查都要考虑：

- 是否需要管理员权限；
- 是否会泄露内部地址或错误详情；
- 是否有超时和降级行为；
- 服务本身不可用时标题栏如何显示。

#### 阶段验收

- 标题栏只增加经过权限和数据口径验证的摘要信号。
- 点击摘要可以下钻到可解释的详情，而不是停留在一个无上下文数字。
- 运营信号统计有明确时间窗口和空数据状态。

## 13. 第四阶段实施记录

> 实施日期：2026-08-03
> 实施状态：已完成，待实际窗口回归和下钻交互验证

本阶段已完成以下改动：

- 在 `DashboardSummaryDto` 增加兼容式 `OperationalSignals` 字段，纳入四类可以从现有数据可靠推导的信号：过去 24 小时登录失败、未来 7 天内到期且尚未撤销的 Refresh Token、启用但缺少 Redirect URI 或允许 Scope 的客户端、过去 24 小时失败审计事件。
- 后端统一使用本次请求的 `utcNow` 作为统计快照时间，避免同一响应中各项统计的时间边界不一致。
- 登录失败统计只查询 `Category=认证`、`Action=登录`、`Outcome=失败` 的审计记录；Token 统计按 `RevokedAtUtc IS NULL`、`ExpiresAtUtc > utcNow` 和 `ExpiresAtUtc <= utcNow + 7 天` 过滤。
- `users.view` 或 `clients.view` 可查看登录失败信号，`clients.view` 可查看 Refresh Token 信号；无权限时仅返回 `IsVisible=false` 和权限说明，前端不显示数值。
- `clients.view` 可查看客户端配置和失败审计信号；客户端配置异常判定为启用客户端缺少 Redirect URI 或允许 Scope，失败审计信号作为待复核代理，不伪造不存在的确认状态。
- 标题栏仅在存在正数运营信号时显示紧凑的“运营提醒 N 项”，详细信号移动到标题栏下方的“运营提醒”区域，避免把每个数字塞入主标题行。
- 每个运营信号详情卡都提供“查看详情”：登录失败和失败审计事件进入带时间/结果筛选的审计日志，Refresh Token 进入“有效 + 7 天内到期”筛选，客户端配置异常进入客户端列表并显示具体缺失项。
- 前端对缺少 `operationalSignals` 的旧服务响应保持兼容，不显示运营提醒，不影响原有摘要、趋势和刷新流程。
